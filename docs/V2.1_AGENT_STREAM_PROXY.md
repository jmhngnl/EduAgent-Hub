# EduAgent Hub V2.1 Round 2 — Java Agent SSE Proxy

This cut connects the deterministic Spring Boot platform plane to the existing FastAPI/LangGraph runtime without rewriting the Python agent.

## New request path

```text
Client
  -> POST /api/conversations/{conversationId}/messages/stream
  -> Spring Boot persists USER message in MySQL
  -> Spring Boot calls FastAPI /v1/chat/stream
  -> FastAPI/LangGraph emits route/token/tool_start/tool_end/done/error
  -> Spring Boot forwards those SSE events
  -> on done, Spring Boot persists ASSISTANT + trace metadata in MySQL
  -> only after persistence succeeds is done forwarded to the client
```

The Java conversation ID is used directly as Python `session_id`. No mapping table is introduced.

## Request

```json
{
  "content": "Flow Matching 和 Diffusion 有什么区别？"
}
```

## Persisted assistant metadata

The existing `chat_message` columns are now populated from the Python stream:

- `task_route`
- `skill_name`
- `tool_calls_json`
- `citations_json`
- `latency_ms`

`token_usage_json` stays null because V1 currently does not emit token-usage events.

## Internal FastAPI authentication

The platform server forwards `X-API-Key` to FastAPI. Docker Compose resolves the value in this order:

```text
PLATFORM_AGENT_API_KEY
-> first key in API_KEYS
-> demo
```

When `API_KEYS` contains multiple comma-separated keys, the platform server uses the first one. You can override it explicitly:

```text
PLATFORM_AGENT_API_KEY=<one-valid-fastapi-key>
```

## Smoke test

Create a conversation:

```bash
CONVERSATION_ID=$(curl -fsS -X POST http://127.0.0.1:8081/api/conversations \
  -H 'Content-Type: application/json' \
  -d '{"workspaceId":"demo"}' | sed -n 's/.*"id":"\([^"]*\)".*/\1/p')

echo "$CONVERSATION_ID"
```

Stream through Java, not FastAPI directly:

```bash
curl -N -X POST \
  "http://127.0.0.1:8081/api/conversations/${CONVERSATION_ID}/messages/stream" \
  -H 'Content-Type: application/json' \
  -d '{"content":"Flow Matching 和 Diffusion 有什么区别？"}'
```

Expected SSE shape:

```text
event:route
data:{...}

event:token
data:"..."

...

event:done
data:{...,"platform_message_id":"...","latency_ms":1234}
```

Then confirm both USER and ASSISTANT rows are durable:

```bash
curl -fsS \
  "http://127.0.0.1:8081/api/conversations/${CONVERSATION_ID}/messages"
```

## Failure behavior

- User message is persisted before the Python call.
- Upstream HTTP/auth failures are returned as an `error` SSE event.
- If Python emits `error`, Java forwards it and does not invent a successful assistant message.
- The MySQL transaction is not kept open while the model is streaming.
- If the browser disconnects, the Java virtual thread may continue consuming the upstream stream so a successful `done` can still be persisted.
